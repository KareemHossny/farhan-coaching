# دليل الإطلاق والإرجاع

هذا الدليل خاص بالإطلاق على Vercel مع مشروع Supabase الحالي. لا تستخدم Supabase reset أو seed على المشروع الحقيقي.

## قبل تطبيق migrations

1. خذ نسخة احتياطية مؤكدة من قاعدة البيانات من لوحة Supabase أو من آلية النسخ الاحتياطي المفعلة في الخطة.
2. احتفظ برقم النسخة ووقت إنشائها، وتأكد أن الاستعادة ممكنة قبل أي تغيير.
3. راجع `supabase/migrations/0006_security_and_client_safe_data.sql` و`0007_atomic_writes.sql`.
4. قارِن عدد السجلات الأساسية في `profiles`, `clients`, `plans`, `plan_items`, `progress_logs`, و`leads` قبل وبعد التطبيق.

## ترتيب قاعدة البيانات

طبّق migrations الجديدة فقط بعد النسخة الاحتياطية:

- `0006_security_and_client_safe_data.sql`
- `0007_atomic_writes.sql`

لا تعدّل أو تعيد تشغيل `0001` إلى `0005`. إذا فشل تطبيق migration، أوقف الإطلاق وراجع الخطأ؛ لا تستخدم reset.

## متغيرات البيئة

في Vercel أضف لكل من Preview وProduction:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `NEXT_PUBLIC_SITE_URL`
- `SUPABASE_SERVICE_ROLE_KEY` — للاستخدام على الخادم فقط، ولا يبدأ اسمه بـ `NEXT_PUBLIC_`.

بعد الإضافة، أعد النشر وتحقق من عدم ظهور المفتاح السري في bundle المتصفح أو السجلات.

## التحقق بعد التطبيق

شغّل محليًا:

```bash
npm ci
npm run typecheck
npm run lint
npm run test
npm run build
```

ثم نفّذ اختبارات العزل بحسابين مختلفين: عميلان ومدربان، وتأكد أن العميل لا يحصل على السعرات أو الماكروز أو ملاحظات المدرب، وأن كل مدرب لا يرى بيانات المدرب الآخر.

## الإرجاع

إذا ظهرت مشكلة في التطبيق، أوقف النشر أو ارجع إلى آخر deployment سليم في Vercel. لا تحذف migrations ولا تحاول عكسها يدويًا دون خطة SQL مراجعة. استعادة البيانات تتم من النسخة الاحتياطية بواسطة مالك مشروع Supabase، مع حفظ سجل الاستعادة ووقت التنفيذ.

## بوابة القبول

لا يعتبر النظام جاهزًا للتسليم قبل نجاح: دخول المدرب، إنشاء عميل، دخول العميل، بناء خطة تمرين وغذاء بالجرام، رفع تقدم، الإيقاف وإعادة التفعيل، إرسال lead، وروابط WhatsApp على الهاتف.
